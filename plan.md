- [x] Confirm CROWDB checks upload integrity before accepting PUT and multipart parts. It requires a signed payload digest, a declared checksum, or Content-MD5, and validates the received bytes before publication.
- [x] Remove the loader's remote HEAD and full-file readback after upload. Also remove the duplicate pre-upload existence check: PyIceberg's `create(overwrite=False)` already performs it. Keep local size validation and report the local SHA-256; let failed upload or stream close stop registration.
- [x] Update upload tests and documentation, then run focused loader checks. Unit suite: 181 passed; transfer/commit/runner subset: 36 passed. Real HTTP integration is skipped because SQLAlchemy is absent.
- [x] Add bounded concurrent uploads with 24 workers by default. Keep table snapshot commits ordered and once per table; serialize report writes and record each upload result safely. Normal SF1/SF10 datasets gain concurrency across tables even when each table has one file.
- [x] Run a small end-to-end import on the current container after the changes. TPC-H SF0.01 passed: 8 tables and 86,805 rows; independent remote footer and Iceberg scan passed.
- [x] Diagnose the previous SF10 `lineitem` commit failure from durable catalog state and server diagnostics before any retry. The server rejected a valid 466,271-byte Parquet footer with 229 row groups because its compact metadata parser budget was 100,000 values. CROWDB now allows 500,000 values within the same 1 MiB footer bound. A focused regression test fails at the old limit and passes at the new limit. After confirming the failed table UUID, empty snapshot, and remote footer/row count, a single recovery commit on the new server succeeded. The original staging and report remain for audit.
- [x] Measure SF1 and SF10 imports with timings and request counters. TPC-H SF1 succeeded in 50 s; SF10 succeeded in 232 s with independent manifest/footer/sample-scan verification. SF10 uploaded 3,635,609,132 bytes across eight files; the upload phase up to first commit took about 176 s, roughly 20.7 MB/s. TPC-DS SF1 succeeded in 157 s; SF10 succeeded in 453 s after the server multipart admission retry fix, with 24 of 24 tables independently verified. Concurrent upload did not improve SF0.01/SF1 wall time in this single-node run. The remaining 20.7 MB/s TPC-H SF10 upload ceiling needs a separate streaming/write-path profile.

TYPE ICEBERG, ENDPOINT 'http://localhost'` and catalog-vended object credentials returned `r_regionkey=1, r_name=AMERICA` from `tpch_parallel_001.region`, a row from the 2.2 GiB SF10 `lineitem` file, and `(i_item_sk=1, i_item_id=AAAAAAAABAAAAAAA)` from the newly loaded `tpcds_parallel_sf10_retry.item`. - [x] Inspect GET latency in the server after the load flow works. In a representative live five-second KV metrics window, 244 GET RPCs averaged 98.9 microseconds (p99 154 microseconds, maximum 278 microseconds), while PUT RPCs averaged 3.95 milliseconds (p99 11.9 milliseconds) and WAL fsync averaged 3.27 milliseconds. Earlier request-local Iceberg measurements counted 127 GET and 24 CAS for a 273 ms create, and 136 GET and 15 CAS for a 203 ms update. Even 127 GET at roughly 0.1 ms each account for only about 13 ms; the GET count alone does not explain multi-second operations. These aggregate metrics are not isolated to a single request, and the 20.7 MB/s SF10 upload bottleneck still needs a separate streaming/write-path profile.

## Current measurements and diagnosis

- Old sequential TPC-H SF0.01: 29.81 s. New concurrent SF0.01: 31 s including generation and validation. Parallelism did not improve this tiny workload; table creation and commit remain serial.
- Old sequential TPC-H SF1: 46 s. New concurrent SF1: 50 s including generation and validation. The comparison is not a controlled benchmark; container state and cache differ.
- The first concurrent SF10 run uploaded all eight Parquet files, committed seven tables, then rejected the 2,330,954,558-byte `lineitem` file at table commit with `Invalid selected table files`. Its local staging and original report were retained. The new server accepted that exact remote file without another upload, and a fresh SF10 run committed all eight tables. This confirms the parser budget was the live cause.
- TPC-DS SF1 loaded 24 tables, 19,557,579 rows, and 277,305,727 compressed Parquet bytes in 157 s. Independent manifest/footer/sample-scan verification passed all 24 tables.
- The first TPC-DS SF10 attempt generated 24 files and 191,500,208 rows, but 24 concurrent multipart initiations hit `SlowDown` on the catalog-wide admission record. No table committed. The server now retries transient pending/CAS contention; a 24-way concurrent create regression test first reproduced the failure and then passed. A fresh run loaded 24 tables, 191,500,208 rows, and 2,774,412,209 compressed Parquet bytes in 453 s. Independent manifest/footer/sample-scan verification passed all 24, and DuckDB queried `item`. The first failed report and local staging remain for audit.
